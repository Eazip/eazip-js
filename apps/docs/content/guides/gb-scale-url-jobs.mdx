title: Zip GB-scale, 1,000+ URL jobs
description: Offload huge, many-file archives to the cloud strategy — splitting, reload-resume, and the limits that actually bite.
---

Browser-side zipping holds everything in tab memory and dies with the tab. At
some point — usually somewhere past a few hundred megabytes, or a few thousand
files — that stops being a tradeoff and becomes the reason the export fails.
`strategy: 'cloud'` hands the same `files` list to Eazip Cloud, which fetches
the sources and builds the archive server-side.

Everything else stays: the same call, the same tray, the same result shape.

## What you need first

- A public key (`pk_ez_…`) — see [Get a public key](/docs/cloud/get-a-public-key)
- Your file **URLs**. Cloud sources are fetched by the API, so `File`/`Blob`
  inputs throw `EazipValidationError('CLOUD_URL_SOURCES_ONLY')`
- The hosts serving those URLs added to your Public App's allowed source hosts

## Start the job

```tsx title="ExportAll.tsx"
'use client';

import { EazipTray, useEazip } from '@eazip/react';

function ExportAll({ urls }) {
  const zip = useEazip();

  return (
    <>
      <button
        onClick={() =>
          zip.download({
            strategy: 'cloud',
            publicKey: process.env.NEXT_PUBLIC_EAZIP_KEY,
            files: urls, // thousands of URLs is the normal case here
            zipName: 'customer-export.zip',
            mode: 'stored',
          })
        }
      >
        Export all files
      </button>
      <EazipTray />
    </>
  );
}
```

`mode: 'stored'` builds the archive once and keeps it, so a customer who
downloads the same export twice gets the same bytes without rebuilding. The
SDK's default is `'stream'`, which regenerates on each download and is usually
ready sooner — see [Stream vs stored](/docs/cloud/stream-vs-stored).

With `@eazip/core` instead of React, it's the same options through `startZip`:

```ts
import { startZip } from '@eazip/core';

const job = startZip({
  strategy: 'cloud',
  publicKey,
  files: urls,
  zipName: 'customer-export.zip',
  mode: 'stored',
});

const result = await job.done;
result.downloadAll(); // one download per output zip
```

## Split the output instead of shipping one huge file

A 40 GB single archive is hostile to download and, on some file systems,
hostile to unzip. Pass `maxZipSizeBytes` and the export comes back as parts:

```ts
zip.download({
  strategy: 'cloud',
  publicKey,
  files: urls,
  zipName: 'export.zip',
  maxZipSizeBytes: 2_000_000_000, // 2 GB per part
});
```

You get one `zips[]` entry per part, each with its own `downloadUrl`, and
`multiZip` / `zipCount` on the job tell you it split. Parts are named
`export_part01.zip`, `export_part02.zip`, … A single file larger than the cap
gets a part of its own, over the cap, rather than failing the export — see
[Multi-zip splitting](/docs/concepts/splitting).

Iterate `zips[]` even when you don't pass `maxZipSizeBytes`: it's always an
array, so code written this way keeps working the day you add splitting.

## Surviving a reload

This is the part a local export can't do at all. The job runs on the server, so
a reload only loses the *client's* attachment to it, and that's recoverable.

`@eazip/react` handles it for you — `useEazip()` persists the session and
reattaches on mount, so a reload mid-export comes back with the tray still
narrating. Nothing to wire up; see
[Persistence & reload-resume](/docs/react/persistence).

With `@eazip/core`, persist the session yourself as soon as it appears and
resume with it:

```ts
const job = startZip({ strategy: 'cloud', publicKey, files: urls });

const { session } = job.getSnapshot();
if (session) {
  sessionStorage.setItem('export', JSON.stringify({
    sessionId: session.sessionId,
    clientSecret: session.clientSecret,
  }));
}
```

```ts
import { resumeZip } from '@eazip/core';

const saved = JSON.parse(sessionStorage.getItem('export') ?? 'null');
if (saved) {
  const job = resumeZip(saved);
  const result = await job.done; // polling picks up where it left off
  result.downloadAll();
}
```

The session appears immediately on create — before the zip is built — so save
it then, not on completion. See [Sessions & resume](/docs/concepts/resume).

## Progress at this scale

`filesTotal` comes from your input list, so progress is meaningful from the
first poll rather than creeping up as the server discovers work:

```tsx
const { task } = useEazip();

task?.progress?.filesCompleted; // e.g. 812
task?.progress?.filesTotal;     // e.g. 4000
```

Status is polling-only today — the SDK backs off between polls and pauses while
the tab is hidden. There's no webhook or SSE channel for the browser SDK.

## The limits that actually bite

| Limit | Where it comes from | What to do |
| --- | --- | --- |
| Max files per session | Your Public App (and your plan) | Raise it on the dashboard, or split into several exports |
| Max total size per session | Your Public App or plan default | Raise it, or drop `maxZipSizeBytes` to keep parts small |
| Retention / link expiry | Your plan (24h by default) | Re-run the export for fresh links |
| One unreachable URL | `failOnUrlError` | See below |

A session that exceeds a ceiling is rejected at create time, before any work
starts — the fix is on the dashboard, not in SDK options.

## Failures in a 4,000-file job

At this scale, assume some URLs will fail. By default a cloud job is
all-or-nothing on fetch errors, which is rarely what a customer-facing export
wants — one dead link shouldn't discard 3,999 good files. Decide explicitly:

```ts
zip.download({
  strategy: 'cloud',
  publicKey,
  files: urls,
  failOnUrlError: false, // keep the archive, report what was skipped
});
```

Then tell the user what they got, rather than implying completeness:

```tsx
const { task } = useEazip();

if (task?.state === 'partial') {
  // task.skippedCount files are missing from the archive
}
```

`<EazipTray />` already narrates the partial state for you. See
[Partial results & errors](/docs/concepts/partial-results) for the taxonomy.

<Callout type="warn" title="A URL that opens in your browser can still fail server-side">
  Cloud fetches come from Eazip's servers, so CORS stops mattering and plain
  reachability starts. `raw.githubusercontent.com` is the usual surprise — it
  serves a browser fine and returns `403` to our fetchers. Use a CDN
  (`cdn.jsdelivr.net` works for npm and GitHub content), your own asset domain,
  or signed bucket URLs.
</Callout>
